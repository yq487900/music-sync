# 内置接口服务的版本监控与热更新

容器里内置了一个 `ncm-api`（`@neteasecloudmusicapienhanced/api`），所有网易云请求
（登录、歌单、取播放地址、云盘）都经它转发。本功能负责：**发现新版本 → 由你决定升不升**。

实现：`app/ncm_upgrade.py`；入口：配置页底部「网易云接口服务」卡片。

---

## 为什么需要它

上游这个包更新很勤，且经常是**修接口**（例如 4.41.0 把 `xeapi` 公钥地址从
`/api/gorilla/...` 换成了 `/api/bsr/sk/get`，旧地址一失效登录和取流就会出问题）。
原先版本号钉死在 `Dockerfile` 的 `ARG NCM_API_VERSION` 里，想跟上就得改代码、
重建镜像、再部署 —— 对「只是换个版本号」来说太重。

现在两条轻量路径：

| | 原来 | 现在 |
|---|---|---|
| 发现新版本 | 自己想起来了去 npm 查 | 每天自动查一次，配置页直接显示 |
| 升级 | 改 Dockerfile → 构建（5~10 分钟）→ 重建容器 | 点一下按钮，**10~20 秒**，只重启 ncm-api 一个进程 |

---

## 检查怎么工作

- 依次问 `registry.npmmirror.com` → `registry.npmjs.org` 要 `dist-tags.latest`
  （国内镜像快，官方源兜底；两个都失败会记 `last_error`，页面显示「检查失败」）。
- 结果缓存进 `config.json` 的 `ncm_api` 段，**一个检查周期内不重复打网络**
  （`check_hours`，默认 24 小时），所以打开配置页是本地读缓存、瞬间出结果。
- 定时任务 `ncm_version_check`：按 `check_hours` 跑，容器启动 2 分钟后先跑一次
  （刚部署完就能看到状态，不用等一天）。
- 版本比较按数字段比较（`4.41.1 < 4.42.0`），不是字符串比较。

---

## 更新怎么工作

点「更新到 x.y.z」（或开了自动更新）后，容器内依次做：

1. **备份**当前包目录到 `/data/ncm-pkg-backup`（失败就直接返回，不动现场）。
2. `npm install @neteasecloudmusicapienhanced/api@<目标版本> --omit=dev --prefix /opt/ncm-api`，
   先后试两个 registry。装完核对 `package.json` 版本号是否真的等于目标版本 ——
   不等就回滚（防止 npm 静默装了别的版本）。
3. **重打启动补丁**：新版 `app.js` 里又是 `checkVersion: true`，必须改回 `false`，
   否则它会在 `listen()` 之前去 `npm info` 卡住，进程活着但不监听 3000（页面整片 502）。
4. **只重启 ncm-api 进程**：`supervisorctl -s unix:///tmp/supervisor.sock restart ncm-api`。
   不重建容器，Web 界面、队列、整理/上传逻辑都不受影响。
5. **健康检查**：轮询 `http://127.0.0.1:3000/login/status`，最多等 150 秒。
   通过才算成功；不通过就**自动回滚**（换回备份目录 + 重启）并报错。
6. 成功后把版本写进 `config.json` 的 `ncm_api.installed_version`。

### 持久化：容器重建不会丢

`/opt/ncm-api` 在容器文件系统里，重建容器就会退回镜像内置版本。所以：

- `Dockerfile` 构建时把 `ARG NCM_API_VERSION` 写到 `/app/.ncm_builtin_version`；
- `entrypoint.sh` 启动时比较 `config.ncm_api.installed_version` 和这个内置版本，
  **不一致就用 npm 装回来**（一致则完全跳过，不联网）；
- 恢复失败不影响容器启动，继续用镜像内置版本（日志里会打一行提示）。

所以热更新过的版本在重建容器、重启 NAS 之后都还在。

## 手动 vs 自动

| 模式 | 行为 | 适用 |
|---|---|---|
| 手动（默认） | 只检查、只提示；你点按钮才升 | 想要「可控」，尤其担心上游改坏接口时 |
| 自动（`auto_update: true`） | 检查到新版本后，**队列空闲时**自动升；队列有下载/上传任务就跳过本轮，下次再说 | 长期不管、希望自动跟上 |

自动模式的两道保险：队列忙时不动（重启会让正在下的歌失败）；升级失败自动回滚。

## 接口

```bash
curl http://<host>:13570/api/ncm/version          # 读缓存状态（不联网）
curl -X POST http://<host>:13570/api/ncm/check    # 立即联网检查
curl -X POST http://<host>:13570/api/ncm/upgrade \
     -H 'Content-Type: application/json' -d '{"version":"4.42.0"}'
curl -X POST http://<host>:13570/api/ncm/auto \
     -H 'Content-Type: application/json' -d '{"enabled":true}'
```

`upgrade` 是异步的（立即返回 `{"started":true}`），进度轮询 `/api/ncm/version`
看 `upgrading` / `stage` / `log`。队列忙时默认返回 409，加 `"force": true` 可强行更新。

状态字段：`current` / `builtin` / `latest` / `has_update` / `checked_at` /
`auto_update` / `check_hours` / `last_error` / `upgrading` / `stage` / `log`。

---

## 配置（`config.json` → `ncm_api`）

```jsonc
"ncm_api": {
  "auto_update": false,        // 发现新版自动升（默认关）
  "check_hours": 24,           // 检查间隔（1~168 小时）
  "installed_version": "",     // 热更新后的版本；entrypoint 按它恢复，空=跟随镜像
  "last_check": "",            // 上次检查时间（自动写）
  "latest": "",                // 上次查到的最新版本（自动写）
  "latest_published": "",
  "last_error": ""
}
```

## 已知限制

1. **更新期间 ncm-api 不可用约 5~15 秒**：正在下载/上传的任务会失败（会正常进重试队列）。
   队列忙时接口默认拒绝，除非 `force`。
2. **容器内要能访问 npm registry**：两个源都不可达时只会提示「检查失败」，
   不影响现有功能（用的是容器里已经装好的版本）。
3. **热更新不改 Dockerfile**：镜像重建后仍会按 `installed_version` 装回来，
   但「长期固定版本」还是应该把 `ARG NCM_API_VERSION` 改掉再发版 ——
   否则每次重建容器都要联网装一次（约 3~10 秒，可接受但不是零成本）。
4. 只支持 `@neteasecloudmusicapienhanced/api` 这一个包，不处理它的依赖升级
   （npm 会自动解析依赖，但我们不做依赖审计）。
